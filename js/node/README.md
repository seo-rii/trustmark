# TrustMark Node.js SDK

A typed Node.js API for embedding and reading TrustMark watermarks on the server, for example
in an image-generation service. It runs the TrustMark ONNX models with
[onnxruntime-node](https://www.npmjs.com/package/onnxruntime-node) and reuses the JavaScript
implementation in this repository: [`tm_core.js`](../tm_core.js) for the image processing and
model calls, and [`tm_datalayer.js`](../tm_datalayer.js) with `deps/bch_ecc.min.js` for packets
and BCH error correction. Nothing is re-implemented here; what the SDK adds is image file
input/output, model file handling, session lifecycle, a job queue and typed results.

The package is `private`: it loads `../tm_core.js`, `../tm_datalayer.js` and
`../deps/bch_ecc.min.js` from this repository, so use it from a checkout (for example as a
`file:` dependency pointing at `js/node`).

## Requirements

- Node.js 20 or later. The SDK relies on the global `fetch`, web streams, `AbortSignal.timeout`
  and the stable `node:test` runner of Node.js 20. It is tested on Node.js 20 and 24.
- The models in a local directory, from
  `https://cai-watermark.adobe.net/watermarking/trustmark-models/`: `encoder_<V>.onnx` to embed,
  and `decoder_<V>.onnx` and `resizer.onnx` to decode, for the variant `<V>` you use (`Q`, `P`,
  `B` or `C`).

```
cd js/node
npm install
```

Dependencies: `onnxruntime-node` (inference), and the small pure JavaScript codecs `pngjs` and
`jpeg-js`, which avoid a second native dependency such as `sharp`. If your service already uses
`sharp` or another decoder, pass raw pixels (see [Images](#images)).

On Linux x64, installing `onnxruntime-node` downloads its CUDA execution provider from NuGet. Set
`ONNXRUNTIME_NODE_INSTALL=skip` for CPU-only or offline installs.

## Quick start

```js
const { createTrustmark } = require('trustmark-node');  // or require('./js/node')

const trustmark = createTrustmark({ modelDir: '/srv/models/trustmark' });

const { bytes, payload } = await trustmark.encode(pngOrJpegBytes, '1011001110001111000011111000001111110000001111111000000011111');
const result = await trustmark.decode(bytes);
// result.status === 'detected', result.payload === payload, result.schema === 'BCH_5'

await trustmark.close();
```

[`examples/generate-and-watermark.mjs`](examples/generate-and-watermark.mjs) shows the step in an
image-generation tool: generated bytes in, watermark, encode the final format, bytes out, and
fail instead of returning the unwatermarked image.

## API

The types are in [`index.d.ts`](index.d.ts).

### `createTrustmark(options)`

Creates an instance for one variant and schema. Create it once per process and reuse it: the
ONNX sessions are created on first use (or by `ready()`) and kept until `close()`.

| Option | Default | |
| --- | --- | --- |
| `modelDir` | required | Directory with the `.onnx` files, or where downloads are stored. |
| `variant` | `'Q'` | Model variant. See `capabilities()` for what the JavaScript core can embed and decode. |
| `schema` | `'BCH_5'` | Schema for embedding: `BCH_SUPER` (40-bit payloads), `BCH_5` (61), `BCH_4` (68) or `BCH_3` (75). |
| `allowDownload` | `false` | Download missing models from `modelBaseUrl`. |
| `modelBaseUrl` | the Adobe model host | `https:` URL; `http:` is only accepted for localhost. |
| `expectedDigests` | none | SHA-256 per file name, e.g. `{ 'encoder_Q.onnx': '19b3…' }`. Checked whenever a model is loaded. |
| `requireDigests` | `false` | Refuse models that have no expected digest. |
| `maxModelBytes` | 256 MiB | Largest model file accepted, local or downloaded. |
| `executionProviders` | `['cpu']` | Tried in order for the encoder and decoder, e.g. `['cuda', 'cpu']` or `[{ name: 'cuda', deviceId: 1 }]`. |
| `sessionOptions` | none | Extra ONNX Runtime session options, e.g. `{ intraOpNumThreads: 4 }`. |
| `maxPixels` | 25,000,000 | Largest image accepted, checked from the file header before decoding. |
| `maxConcurrency` | 1 | Calls that run at the same time. Others wait in a FIFO queue. |
| `maxQueue` | 100 | Calls that may wait; more fail with `QUEUE_FULL`. `Infinity` is allowed. |
| `orientation` | `'apply'` | EXIF orientation of input files; see [Images](#images). |
| `fetch`, `ort` | globals | Replace `fetch` (downloads) or the ONNX Runtime module. |

### `encode(input, payload, options?)`

Embeds `payload` and returns `{ bytes, format, mimeType, quality, payload, schema, variant,
strength, backend, width, height }`. It rejects with a `TrustmarkError` rather than ever
returning an image without a watermark.

- `payload` is a string of `0` and `1` characters, at most the schema capacity. Shorter payloads
  are padded with zeros, as in Python; the result's `payload` is the padded value that was
  embedded. Numbers are rejected: a 61-bit payload does not fit in a JavaScript number.
- `options.format` is `'png'` (default, lossless) or `'jpeg'` with `options.quality` (1 to 100,
  default 90).
- `options.strength` (default 1.0) scales the watermark, like `WM_STRENGTH` in Python.
- `options.background: [r, g, b]` flattens transparent pixels onto that colour before embedding.
  It is required for JPEG output of an image with transparency.
- `options.signal` is an `AbortSignal`.

### `decode(input, options?)`

Resolves with `{ status, payload, schema, variant, backend, bitFlips, softBinding, error }`:

| `status` | Meaning |
| --- | --- |
| `detected` | A watermark was found: `payload` (at the full schema capacity), `schema`, the number of bits the BCH code corrected, and the C2PA soft binding assertion. |
| `not_detected` | The decoder ran and found no watermark. |
| `error` | The image could not be checked (unreadable image, missing or corrupt model, inference failure). `error` is the `TrustmarkError`. The image may still carry a watermark. |

`decode` rejects (instead of resolving with `error`) on invalid arguments, an aborted signal,
`QUEUE_FULL` and `CLOSED`.

`options.schemaPolicy` decides which schemas count as a detection. The two version bits that
name the schema are not protected by the error correction, and every schema accepts some packets
read from unwatermarked images (for random packets about 0.15% for `BCH_5`, 1.6% for `BCH_4`
and 8.7% for `BCH_3`):

- `'signalled'` (default): only the schema named by the version bits, like the Python
  implementation (about 2.4% of random packets).
- `'any'`: any schema that error-corrects the packet, like `runwmark` in the browser demo. This
  tolerates corrupted version bits but accepts about 10% of random packets. On the three
  unwatermarked repository images, it reported `BCH_3` watermarks for variant B on `ghost.png`
  and `ripley.jpg` and for variant C on `ripley.jpg`; `'signalled'` reported none.
- a schema name such as `'BCH_5'`: only that schema, whatever the version bits say. Use this when
  you only embed one schema; it has the lowest false positive rate.

A detection is evidence, not proof: compare the payload with the payloads you issued.

### `encodeVerified(trustmark, input, payload, options?)`

For pipelines that must never release an image without a readable watermark. It embeds the
payload, encodes the final format and quality, decodes those exact bytes again and resolves only
when the payload and the schema read back exactly. The result is the `encode` result plus
`sha256` (of `bytes`) and `verification` (`payload`, `schema`, `bitFlips`, `backend` and every
attempt). Otherwise it rejects with a `WatermarkVerificationError` (code `VERIFICATION_FAILED`)
whose `reason` is `not_detected`, `payload_mismatch`, `schema_mismatch`, `decode_error` or
`bytes_changed` (a custom verifier modified the bytes), and whose `attempts` describe each try. It never returns the input or bytes that failed, and the
error carries no image bytes.

- The check uses the `'signalled'` schema policy, so the version bits must also be intact, as the
  Python decoder requires.
- `options.retryStrengths`, e.g. `[1.5, 2]`, are higher strengths to try, in order, when the
  watermark is not read back. There are no retries by default, and a decoder error is not
  retried. With the Q models, `ufo_240.jpg` saved as JPEG at quality 20 passed at strength 1,
  at quality 15 it needed strength 2, and at quality 10 or less nothing up to strength 3 passed.
- `options.verifier` decodes with another object that has `decode()`, for example a second
  instance on a different execution provider. By default the same instance is used.
- `format`, `quality`, `background`, `strength` (first attempt) and `signal` are as for `encode`.
  Encode errors and aborts reject as they do for `encode`.

This is the reusable, policy-free part of a release gate. Which images may be published, by
whom, and where, belongs to the service that calls it.
[`examples/verified-release/release.mjs`](examples/verified-release/release.mjs) shows one way to
use it: the generated image stays in a private directory, `encodeVerified` produces the verified
bytes, which are staged privately and published into a public directory with an atomic,
no-clobber hard link; a JSON record per job id tracks `generated`, `verified`, `released` or
`failed`, and a released job id is not processed again. Failures before publication leave the
original private. The hard link commits the release: subsequent record or cleanup errors return
`state: 'released'` with `warnings` entries (`operation`, `path`, `code`, `message`). A retry checks
the public file against the durable verification digest and completes the release record and
original cleanup without encoding again. A staging-cleanup warning names the private file left
for cleanup. `examples/verified-release/demo.mjs` reports these warnings from the command line.

What this does not guarantee:

- It is not authentication or proof of origin. Anyone with the public models can read a payload,
  and a watermark can be removed or copied onto another image. Use signed C2PA manifests for
  provenance, and treat the payload as a lookup key.
- The storage or gateway is the enforcement point: serve only the public directory, deny access
  to the private one, and make sure nothing else writes to the public directory.
- Job ids and payloads are not secrets.
- Verification uses this SDK's decoder on the final bytes. Other decoders can differ on marginal
  JPEGs, and later resizing or recompression can remove the watermark.
- It is not a legal or regulatory compliance guarantee.

### `ready(options?)`, `status()`, `close()`

`ready()` loads the models now (useful at startup, so that a missing model fails fast) and
resolves with `status()`. `status()` reports per model (`resizer`, `encoder`, `decoder`) the
state, the providers requested, the provider in use (`backend`), providers that failed
(`fallbacks`), the file path, size and SHA-256, whether it matched an expected digest, and
whether it was downloaded.

`close()` rejects waiting calls with `CLOSED`, stops downloads, waits for running calls and
releases the ONNX sessions. Later calls reject with `CLOSED`.

### `capabilities()`

Returns the variants the JavaScript core can embed and decode, and the schemas with their
capacities. The SDK reads the variants and their model names from `TrustmarkCore.VARIANTS` in
`tm_core.js`: Q, P, B and C, each of which embeds and decodes with every schema.

### Errors

Every error is a `TrustmarkError` with a `code`, except aborts, which reject with the signal's
reason (an `AbortError` or `TimeoutError` `DOMException` by default):

| Code | |
| --- | --- |
| `INVALID_ARGUMENT` | Invalid option, payload, strength or raw image. |
| `UNSUPPORTED` | Variant, schema or format not supported, or transparency with JPEG output. |
| `INVALID_IMAGE` | Not a readable PNG or JPEG. |
| `IMAGE_TOO_LARGE` | More pixels than `maxPixels`. |
| `MODEL_NOT_FOUND` | A model file is missing and downloads are disabled. |
| `MODEL_DOWNLOAD_FAILED` | A download failed. |
| `MODEL_INTEGRITY` | A model is larger than `maxModelBytes`, does not match its digest, or has no digest with `requireDigests`. |
| `MODEL_LOAD_FAILED` | No execution provider could create a session; `details.fallbacks` has the reasons. |
| `INFERENCE_FAILED` | A model failed while running. |
| `QUEUE_FULL`, `CLOSED` | See `maxQueue` and `close()`. |
| `VERIFICATION_FAILED` | `encodeVerified` could not read the watermark back (`WatermarkVerificationError`). |

## Models

The SDK only reads models from `modelDir`. With `allowDownload: false` (the default) it never
uses the network, so a service behaves the same offline as online and never fetches unreviewed
code-like artifacts at run time; provision the models with the deployment instead. A missing
model is reported as `MODEL_NOT_FOUND`, never as "no watermark".

With `allowDownload: true`, missing files are downloaded once (concurrent calls share the
download) into a temporary file in `modelDir`, checked against `maxModelBytes` and the expected
digest, flushed and renamed into place, so a failed or interrupted download never leaves a
partial model behind. Model files are read into memory and hashed before the session is created
from those same bytes. The model host does not publish digests yet; record the SHA-256 of the
files you reviewed and pass them in `expectedDigests`.

## Images

Inputs are PNG or JPEG bytes (`Buffer`, `Uint8Array` or `ArrayBuffer`), or raw 8-bit pixels
`{ data, width, height }` (RGBA, or RGB with `channels: 3`), e.g. from `sharp(...).raw()`.

- EXIF orientation (JPEG `APP1` and PNG `eXIf`) is applied by default, like Pillow's
  `ImageOps.exif_transpose`, so the watermark is embedded in the image as viewers display it.
  Outputs carry no metadata, so they display the same in every viewer. With `orientation:
  'ignore'` the stored pixels are used as they are.
- PNG output keeps the alpha channel (an RGB PNG is written when every pixel is opaque). As in
  the other implementations, the models only see RGB; alpha is copied unchanged.
- Output files contain no metadata: EXIF, XMP, ICC profiles and C2PA manifests of the input are
  not copied. Colour values are used as stored, without colour management.
- 16-bit PNGs are reduced to 8 bits per channel.

## Execution providers

The encoder and decoder run on the first provider in `executionProviders` that can create a
session; each provider is tried on its own, so `backend` and `status()` report the one in use and
why the others failed. ONNX Runtime still runs operators that a provider does not support on the
CPU. The small resizer model, which downscales images for the decoder, always runs on the CPU, so
the decoder input is the same on every provider. Embedding downscales in JavaScript.

For `'cuda'`, `onnxruntime-node` 1.30 needs its CUDA provider libraries (downloaded at install
time on Linux x64) and the CUDA 13 runtime, cuBLAS, cuRAND and cuDNN 9 libraries on the library
path, with a matching NVIDIA driver. In a test on an A100 (driver 580, CUDA 13.0 runtime and
cuBLAS, cuDNN 9.26) with variant Q, watermarks embedded on the GPU differed from CPU ones by at
most one level in about 6% of the bytes, and decoded exactly on either.

## Concurrency and cancellation

Calls run through a FIFO queue, at most `maxConcurrency` at a time. Each call checks its
`signal` while waiting, between steps and around every inference; ONNX Runtime cannot stop an
inference that has started, so an abort takes effect when it ends. Image decoding, the pixel
processing in `tm_core.js` and PNG/JPEG encoding run on the calling thread; for higher
throughput, run several processes or worker threads, each with its own instance.

## Limitations

- Embedding reproduces Python's Pillow downscale exactly, and differs from Python's output by at
  most one level per channel (see [the JavaScript README](../README.md)). Decoding downscales with
  `resizer.onnx` (antialiased bicubic), where Python uses Pillow's bilinear resize, and the ONNX
  decoders of B, C and Q take 256x256 inputs where Python's run at 245x245. Watermarks embedded
  by either implementation decode in both.
- Like the Python implementation, small images and payloads that are mostly zeros are harder to
  decode, especially with variant P and the `BCH_4` and `BCH_3` schemas.
- JPEG decoding uses `jpeg-js`, whose output differs by a few levels from libjpeg; a JPEG that
  barely decodes here may decode differently elsewhere.

## Tests

```
cd js/node
npm test
```

The unit tests need neither the models nor the network: ONNX Runtime is replaced by a fake, and
downloads go to a local HTTP server. `test/offline.test.mjs` runs the SDK in a child process that
blocks and records every socket, DNS lookup and `fetch`. The type definitions are checked with
`tsc --noEmit` (`npm run typecheck`).

Model-backed tests are skipped, with the reason, unless the models are available:

```
TRUSTMARK_MODEL_DIR=/path/to/models npm test
```

The cross-checks with the Python implementation need the models of all four variants and an
interpreter with the dependencies of `python/trustmark` and the checkpoints of all four variants:

```
TRUSTMARK_MODEL_DIR=/path/to/models TRUSTMARK_PYTHON=/path/to/venv/bin/python \
  TRUSTMARK_PYTHONPATH=/path/to/dir/containing/trustmark npm test
```
